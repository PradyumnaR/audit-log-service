# Architecture

## Summary

The Audit Log Service is a tamper-evident, append-only audit log built with Python 3.13, FastAPI, Pydantic, SQLAlchemy and SQLite. Callers write events (who did what, to which resource, when) and query them, but can never update or delete them. Each record is linked to the previous one by a SHA-256 hash over canonically serialized content, forming a hash chain. A verification endpoint walks the chain and reports the first broken record and the type of violation.

Operator-only scripts handle retention and redaction without breaking the chain. Retention archives records older than a configurable window, and redaction removes sensitive payload values that are protected by salted field hashes. Records for an actor or resource can be exported as a bundle that anyone can verify offline.

A read-only compliance report shows regulators who viewed, updated or exported client account data in a time range.

| scenario-a | • **Append-only:** events can be written and queried, never updated or deleted.<br>• **Timestamps:** set by the server in UTC ISO 8601 with `Z`, so there is one source of truth for ordering.<br>• **Hash chain:** each record's SHA-256 hash covers its event fields plus the previous hash, serialized as canonical JSON (sorted keys, fixed format). | scenario-b | • **Retention:** run by an operator script (`make retention`) using `RETENTION_DAYS` from `.env`. There is no public endpoint for it, so it can't be misused.<br>• **Archiving:** sets `archived = true` and clears event content, keeping only id, timestamp, contentHash and previousHash so the chain stays linked. Archived records are not returned by queries.<br>• **Archive validation:** archived records must be one continuous block starting at the first record, because retention always archives oldest first. Top-level payload keys listed in the `SENSITIVE_FIELDS` config each get a random 32-byte salt and a field hash of SHA-256(salt + canonical value). The content hash uses the field hash in place of the raw value, so removing the value later doesn't change the content hash.<br>• **Redaction:** run by an operator script (`make redact ID=… FIELD=…`). It removes the value and its salt without changing any stored hash, and it isn't exposed through the API, so the API stays append-only. It refuses fields not in `SENSITIVE_FIELDS`, archived records and fields already redacted. Redacted values are shown as `"[REDACTED]"`.<br>• **Verify with sensitive fields:** if the value and salt are present, verify checks that SHA-256(salt + value) matches the field hash. If the field has been redacted, that check is skipped.<br>• **Export:** `GET /audit/export?actorId=…` or `?resourceType=…&resourceId=…` (resourceId requires resourceType, same as queries). ## Implementation

### Storage: `audit_events` table (`src/audit_log/storage/models.py`)

| Column          | Type               | Hashed          | Notes                                                                                         |
| --------------- | ------------------ | --------------- | --------------------------------------------------------------------------------------------- |
| `id`            | integer PK         | No              | Chain order number. SQLite `AUTOINCREMENT`, so ids strictly increase and are never reused     |
| `event_type`    | string(64)         | Yes             | Indexed                                                                                       |
| `actor_id`      | string(255)        | Yes             | Indexed                                                                                       |
| `resource_type` | string(64)         | Yes             | Indexed together with `resource_id`                                                           |
| `resource_id`   | string(255)        | Yes             |                                                                                               |
| `payload`       | JSON               | Yes (partially) | Sensitive keys are left out of the hash; their field hashes are hashed instead               |
| `timestamp`     | string(20)         | Yes             | The exact canonical string that is hashed (`YYYY-MM-DDTHH:MM:SSZ`); sorts correctly as text   |
| `content_hash`  | string(64)         | n/a             | Hex SHA-256                                                                                   |
| `previous_hash` | string(64)         | Yes             | Hex SHA-256; the genesis value for the first record                                           |
| `archived`      | boolean            | No              | Default false; set by retention                                                               |
| `field_hashes`  | JSON `{key: hash}` | Yes             | Default `{}`                                                                                  |
| `field_salts`   | JSON `{key: salt}` | No              | Default `{}`; hex encoded 32-byte salts; an entry is removed on redaction                     |

The event content columns are nullable only so retention can clear them. A check constraint requires them on every row that is not archived.

### Hashing (`src/audit_log/domain/hashing.py`)

All hashing lives in this one module. It uses only the standard library, so scripts can reuse it without the service or database.

- **Canonical JSON:** `json.dumps(sort_keys=True, separators=(",", ":"), ensure_ascii=False, allow_nan=False)`, encoded as UTF-8.
- **Content hash:** SHA-256 over the canonical JSON of `{eventType, actorId, resourceType, resourceId, timestamp, payload, fieldHashes, previousHash}`. Here `payload` has the sensitive keys (those in `fieldHashes`) removed. `archived` and `fieldSalts` are not included.
- **Field hash:** SHA-256(raw salt bytes + UTF-8 canonical JSON of the value). The salt comes from `secrets.token_bytes(32)`, one per field per record.
- **Genesis:** `6a09e667bb67ae853c6ef372a54ff53a510e527f9b05688c1f83d9ab5be0cd19`, the first 32 bits of the fractional parts of the square roots of the first 8 primes.

### Appending to the chain (`src/audit_log/storage/repository.py`)

`append_event(session, NewEvent)` saves one record and commits. Inside a single transaction it:

1. Reads the `content_hash` of the record with the highest `id`. If the table is empty it uses the genesis hash. Archived records keep their `content_hash`, so they still provide the link.
2. Assigns the server timestamp.
3. Salts and hashes the `SENSITIVE_FIELDS` keys, then computes the content hash with `domain/hashing.py`.
4. Inserts the record.

**Write lock:** on SQLite, `make_engine` makes every transaction start with `BEGIN IMMEDIATE`, so the database write lock is taken at the transaction's first statement. Parallel appends therefore run one at a time: each one waits for the lock (pysqlite's default 5 s busy timeout), then sees the record committed before it. Because the timestamp is also taken under the lock, timestamps never decrease in `id` order. The trade-off is that reads also take the lock while their transaction is open. That is acceptable at SQLite scale.

### Configuration (`src/audit_log/config.py`)

- `SENSITIVE_FIELDS`: comma-separated top-level payload keys. Empty by default.
- `DATABASE_URL`: SQLAlchemy URL. Defaults to `sqlite:///./audit_log.db`.
